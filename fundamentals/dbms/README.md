# Database Management System (DBMS)

## Overview & Architecture

* **Data** is a collection of raw facts or values that represent information about an object, event, or person.
* **Information** is processed data that has meaning.
* A **database** is an organized collection of related data that is stored electronically so it can be easily accessed, managed, updated, and retrieved.
* A **Database Management System (DBMS)** is software that allows users and applications to create, store, retrieve, update, delete, and manage data in a database.

### Database Architecture
**Database Architecture** refers to how users, applications, and the database interact with one another. A database architecture generally consists of:
* **User (Presentation Layer):** This is where users interact with the app.
* **Application Layer:** This contains the business logic.
* **DBMS Layer:** The DBMS receives SQL.
* **Database:** Actual storage.

#### Types of Database Architecture
* **One-Tier:** Everything (User, Database, App) exists in one machine.
* **Two-Tier:** Client directly talks to database (Client to DB Server).
* **Three-Tier:** Client, Application Server, Database Server.

#### Thin Client vs Thick Client
* **Thick Client:** Most processing happens on client.
* **Thin Client:** Most processing happens on server.

#### Client-Server Model
* **Database Server:** A machine running a DBMS.
* **Application Server:** A server that contains business logic.

## Relational Model

* The **Relational Model** is a way of organizing data into **relations (tables)** consisting of **rows (tuples)** and **columns (attributes)**, while defining relationships between them. Instead of storing everything together, we divide data into multiple related tables.
* `Relation != Relationship`, `Relation = Table`
* The relationships between tables are created using **keys**.
* **A Relation is a table.**
* A **tuple** is one row of a relation.
* An **attribute** is a column.
* A **domain** is the set of valid values an attribute can have.
* **Schema** is the structure of the database. It defines:
  * Tables
  * Columns
  * Data Types
  * Constraints
  * Relationships
* **Instance** means actual data stored currently.
* **Degree** = Number of columns.
* **Cardinality** = Number of rows.

## Keys

A **key** is one or more attributes (columns) used to uniquely identify a tuple (row) in a relation (table).

* **Super Key:**
  * A Super Key is any set of attributes that uniquely identifies a row.
  * It may contain extra unnecessary attributes.
  * `Super Key = Unique + May contain extra columns`
* **Candidate Key:**
  * A Candidate Key is the smallest possible Super Key.
  * No unnecessary attributes.
  * `Candidate Key = Minimal Super Key`
* **Primary Key:**
  * A Primary Key is the Candidate Key chosen to uniquely identify every row.
  * Rules for selecting a candidate key as primary key:
    * Cannot be NULL
    * Cannot contain duplicates
    * Only one Primary Key per table
    * Must uniquely identify rows
* **Alternate Key:**
  * Candidate Keys that are not selected as Primary Key.
* **Foreign Key:**
  * A Foreign Key is an attribute in one table that refers to the Primary Key of another table.
  * It creates or establishes relationships between tables.
  * It enforces a constraint on the attribute: every value in the foreign key must exist in the primary key attribute.
  * Foreign Key ensures every referenced value must exist in the parent table.
* **Composite Key:**
  * A key made from **multiple columns**.
  * Neither StudentID nor CourseID alone is unique. Together `StudentID + CourseID` uniquely identify each row.
* **Unique Key:**
  * Looks similar to Primary Key. Difference:
    * **Primary Key:** Only One, No NULL
    * **Unique Key:** Multiple Allowed, Usually allows NULL (because NULL values are not considered equal)
    * Both of them allow us to identify rows uniquely.
* **Natural Key:**
  * A key that already exists in the real world.
  * E.g., Aadhaar Number, PAN, Passport Number, etc.
* **Surrogate Key:**
  * Artificial key generated by database.
  * Advantages: Short, Never Changes, Fast Indexing

## Constraints

**Constraints** are rules enforced by the DBMS on table columns to ensure the accuracy, consistency, and integrity of the data.

### Types of Constraints
* **NOT NULL:** A NOT NULL constraint ensures that a column must always have a value.
* **UNIQUE:** Ensures that all values in a column (or combination of columns) are unique.
* **PRIMARY KEY:** `Primary Key = Not Null + Unique`. Only one PRIMARY KEY per table.
* **FOREIGN KEY:** Ensures every referenced value must exist in the parent table. Referential Integrity: Child records cannot point to non-existing parent records.
* **CHECK:** Allows only values satisfying a condition. E.g., `CHECK (age >= 18)`.
* **DEFAULT:** Provides a default value when no value is supplied.
* **AUTO_INCREMENT / SERIAL / IDENTITY:** Used for serializing the rows and encoding each of them with an id which helps us with faster indexing.

### Referential Actions
* **ON DELETE/UPDATE CASCADE:** Delete Parent: delete children automatically.
* **ON DELETE/UPDATE RESTRICT:** Parent cannot be deleted while children exist.
* **ON DELETE/UPDATE SET NULL:** Delete Parent: Foreign key becomes NULL.
* **ON DELETE SET DEFAULT:** Foreign key becomes its default value.
* **NO ACTION**

## SQL (Structured Query Language)

**SQL (Structured Query Language)** is the standard language used to create, retrieve, update, delete, and manage data in relational databases.

### Categories of SQL Commands

#### 1. DDL (Data Definition Language)
Defines or changes the **structure** of the database.
Commands:
* **CREATE:** Creates new objects (Tables, View, Index, etc).
* **ALTER:** Modifies an existing table (Add, Drop, Rename, Modify column).
* **DROP:** Deletes an object completely.
* **TRUNCATE:** Deletes **all rows** but keeps the table structure.
* **RENAME:** Rename table.

#### 2. DML (Data Manipulation Language)
DDL changes structure; DML changes **data**.
Commands:
* **INSERT:** Adds rows.
* **UPDATE:** Modify existing rows.
* **DELETE:** Deletes rows.

#### 3. DQL (Data Query Language)
Commands:
* **SELECT:** Retrieves data from tables.

#### 4. DCL (Data Control Language)
Used for permissions or permission management.
Commands:
* **GRANT:** Give permission.
* **REVOKE:** Remove permission.

#### 5. TCL (Transaction Control Language)
Used with transactions.
Commands:
* **COMMIT:** Save changes permanently.
* **ROLLBACK:** Undo changes.
* **SAVEPOINT:** Create a checkpoint.

### CRUD Operations
* **Create:** `INSERT`
* **Read:** `SELECT`
* **Update:** `UPDATE`
* **Delete:** `DELETE`

## Aggregate Functions

An **Aggregate Function** performs a calculation on **multiple rows** and returns a **single value**.

### List of Aggregate Functions
* **COUNT:** Returns the number of rows.
  * `COUNT(column)`: Counts only non-NULL values.
  * `COUNT(*)`: Counts every row.
* **SUM:** Returns total.
* **AVG:** Returns average.
* **MIN:** Returns smallest value.
* **MAX:** Returns largest value.
* **STRING_AGG:** Combines multiple strings.
  ```sql
  SELECT STRING_AGG(name, ', ') FROM employees;
  ```
* **ARRAY_AGG:** Returns an array.
  ```sql
  SELECT ARRAY_AGG(name) FROM employees;
  ```

### Key Notes on Aggregate Functions
* Aggregate functions ignore NULL values.
* Aggregate functions become much more powerful with `GROUP BY`.
* **DISTINCT with Aggregate Functions:**
  * Without `DISTINCT`: All of the values are considered.
  * With `DISTINCT`: Only unique values are considered.
* **HAVING vs WHERE:**
  * `WHERE`: Filtering rows.
  * `HAVING`: Filtering groups.
* **Execution Order in a SQL Query:**
  `FROM` -> `WHERE` -> `GROUP BY` -> `HAVING` -> `SELECT` -> `ORDER BY`
* Aggregate functions often scan many rows.
* Indexes can help in some situations (especially for MIN, MAX, or indexed grouping), but many aggregate queries still require scanning a significant portion of the table.

## Joins

A **JOIN** combines rows from **two or more tables** based on a related column.

* **INNER JOIN:**
  * Returns only matching rows from both tables.
  * Only the intersection.
* **LEFT JOIN (or LEFT OUTER JOIN):**
  * Return all rows from LEFT table and matching rows from RIGHT table.
* **RIGHT JOIN (or RIGHT OUTER JOIN):**
  * Return all rows from RIGHT table and matching rows from LEFT table.
* **FULL OUTER JOIN:**
  * Return everything: matching rows, unmatched left rows, unmatched right rows.
* **CROSS JOIN:**
  * Every row with every row (Cartesian Product).
  * 3 rows * 4 rows = 12 Rows.
* **NATURAL JOIN:**
  * Automatically joins columns with the same name.
  * Eg: If both tables have column name "StudentID", DB automatically joins based on that common column without explicitly mentioning it.
  * *Problem:* If another column accidentally has the same name, results may change unexpectedly. Therefore, most developers prefer explicit joins using `ON`.

## Set Operations

Set Operations combine the **results of two or more SELECT queries** into a single result.

* Both queries must have the same number of columns and corresponding columns should have compatible data types.
* Unlike joins, they combine **rows**, not columns.

### Types of SET Operations
* **UNION:** Combines both query results, removes duplicates.
* **UNION ALL:** Combines both query results, doesn’t remove duplicates.
* **INTERSECT:** Returns rows present in both of the queries.
* **EXCEPT (MINUS in Oracle):** Returns rows in the first query that are NOT present in the second query.

## Window Functions

A **Window Function** performs calculations across a group of related rows **without collapsing them into a single row**.
* **Aggregate Function:** One output per group.
* **Window Function:** One output per row.

The term **WINDOW** means: a subset of rows visible to the current row.
* Keyword used for window functions: `OVER()`
* `PARTITION BY` is used alongside `OVER()`

### Types of Window Functions

#### 1. Ranking
* `ROW_NUMBER`: Assigns unique sequential numbers.
* `RANK`: Handles ties: skips ranks.
* `DENSE_RANK`: Handles ties: doesn’t skip ranks.
* `NTILE(4)`: Splits rows into groups (here: quartiles).

#### 2. Value
* `LAG`: Returns previous row.
* `LEAD`: Opposite of `LAG`.
* `FIRST_VALUE`: Returns first value in partition.
* `LAST_VALUE`: Returns last value in partition.
* `NTH_VALUE`: Returns n-th row.

#### 3. Aggregate
All aggregates can become window functions: `SUM`, `AVG`, `COUNT`, `MIN`, `MAX`.
* Know how to calculate moving average and using `OVER` keyword for window functions.

### Window Functions Syntax Components
`OVER()`:
* `PARTITION BY`
* `ORDER BY`
* `ROWS`
* Ranking
* Value
* Aggregate

## Views

* **Can I save a SQL query and use it like a table?** That's exactly what a View is.
* A **View** is a **virtual table** created from the result of a SQL query.
* A VIEW doesn’t store a table, instead it stores the SQL query.

### Usage Example
Suppose we have 2 tables and we need to run the following query on a daily basis:
```sql
SELECT e.name, d.department, e.salary 
FROM employees e 
JOIN departments d ON e.departmentid = d.departmentid;
```
Instead of running that every day, we can create a view:
```sql
CREATE VIEW employee_details AS 
SELECT e.name, d.department, e.salary 
FROM employees e 
JOIN departments d ON e.departmentid = d.departmentid;
```
Now, instead of writing JOIN everytime we need that data we can simply use:
```sql
SELECT * FROM employee_details;
```

### Updateable Views
Some views are updateable. A VIEW is updateable when it:
* Uses a single base table
* Does not use aggregate functions
* Does not use `GROUP BY`, `DISTINCT`, `UNION`, complex `JOINS`, or set operations

```sql
DROP VIEW employee_details;
CREATE OR REPLACE VIEW employee_details AS SELECT ...;
```

### Types of Views
* **Normal View:** Stores query only.
* **Materialized View:** Stores actual result set.
```sql
REFRESH MATERIALIZED VIEW sales_summary;
```

## Indexing

An **Index** is a special data structure that allows the database to locate rows quickly without scanning the entire table.
* Indexes do not change our data, they only provide a faster way to find it.
* **Why Not Always Use Full Table Scan?** Suppose there are 100 million rows, searching last row without index would need 100 million comparisons… with index 20-30 comparisons are enough.

### Types of Indexes
* **Primary Index:** Created on primary key automatically by DB.
* **Secondary Index:** Created on non-primary columns by user.
  ```sql
  CREATE INDEX idx_name ON employees(name);
  ```
  Now, searching by name becomes faster.
* **Clustered Index:**
  * The table itself is stored in the index order.
  * This index actually determines how rows are physically arranged.
  * Only one clustering order is possible per table.
  * Example: `students` table stored by `StudentID`.
* **Non-Clustered Index:**
  * Creates a separate structure.
  * Table remains unchanged, index stores pointers to rows.
  * We can have many non-clustered indexes, providing fast lookups.
* **Composite Index:**
  * Indexing on multiple columns at the same time, useful when queries filter by both.
  * Follows the **Left-Most-Prefix rule**:
    * Index of `(A, B, C)` will work efficiently for querying on `(A)`, `(A, B)`, and `(A, B, C)`, but not efficient on `(B)`, `(B, C)`, etc.
* **Unique Index:** Ensures no duplicates; if there’s a duplicate it rejects.
* **Partial Index:** Index only on selected rows (smaller index, faster querying, less storage).
* **Function-Based Index:** Index based on an expression.
* **Hash Index:** Uses hash table, supports equality operations only.
* **B-Tree Index:** Self-balancing tree data structure with multiple children and keys. Takes a bit of time for insertions, making queries efficient. Supports both equality and range queries.

### Index Commands & Operations
```sql
CREATE INDEX idx_salary ON employees(salary);
DROP INDEX idx_salary;
EXPLAIN ...;
EXPLAIN ANALYZE ...;
```

### Trade-offs of Indexing
* **Without indexes:** Inserting is simple… directly inserting data into the table.
* **With indexes:** Need to insert row, update index1, update index2, update index3, etc… more work = more time.
* **Rule of Thumb:** Avoid indexing for small tables.

## Normalization & Decomposition

**Normalization** is the process of organizing data into well-structured tables to:
* Reduce redundancy (duplicate data)
* Eliminate anomalies
* Improve data integrity
* Make the database easier to maintain

*Redundancy* means storing the same information multiple times.

### Database Anomalies
Normalization prevents three anomalies:
1. **Update Anomaly**
2. **Insertion Anomaly**
3. **Deletion Anomaly**

*Solution:* Split large tables into smaller related tables.

### Functional Dependency (FD)
* An attribute **Y** is functionally dependent on **X** if each value of **X** determines exactly one value of **Y**.
* **Full Functional Dependency:** Suppose Composite Key `(StudentID, CourseID)` determines `Grade`. Here we need both columns to determine, so it is called Full Functional Dependency.
* **Partial Functional Dependency:** To determine `StudentName` we only need `StudentID`, so it is called Partial Functional Dependency.
* **Transitive Dependency:** `StudentID -> DepartmentID -> DepartmentName` (StudentID and DepartmentName have an indirect functional dependency).

### Normal Forms
* **1NF (First Normal Form):** Every column must contain atomic (indivisible) values, no multiple values. One cell should only contain a single value.
* **2NF (Second Normal Form):** 1NF + No Partial Dependency. Solution: Split Tables.
* **3NF (Third Normal Form):** 2NF + No Transitive Dependency.
* **BCNF (Boyce-Codd Normal Form):** For every dependency `X -> Y`, `X` must be a super key.
* **4NF (Fourth Normal Form):** Handles Multivalued dependency.
* **5NF (Fifth Normal Form):** Handles Join Dependency.

### Decomposition
The process of breaking a large table into smaller tables to achieve good database design through normalization.
* **Lossless Decomposition:** After splitting, joining tables must recover original data (no information should be lost).
* **Dependency Preservation:** All functional dependencies should remain enforceable after decomposition.

## Denormalization & Database Architectures (OLTP vs OLAP)

**Denormalization** is the process of intentionally introducing redundancy into a database to improve read performance.
* Merging tables for performance is said to be denormalization.
* Instead of JOINing 5 tables, store the data in a single table.
* Faster reads, but more redundancy.

### OLTP vs OLAP
* **Normalization is good for OLTP (Online Transaction Processing):**
  * Optimizes operations on large databases with frequent writes.
  * Examples: Banking, UPI, E-commerce, Hospital.
  * Normalization preferred.
* **Denormalization is good for OLAP (Online Analytical Processing):**
  * Designed for reporting, dashboards, business intelligence, and analytics where reads dominate.
  * Denormalization preferred.

| Architecture Type | Read Speed | Write Speed |
| --- | --- | --- |
| **Normalized** | Slow | Fast |
| **Denormalized** | Fast | Slow |

### Star Schema vs Snowflake Schema

| Star Schema | Snowflake Schema |
| --- | --- |
| Denormalized dimensions | Normalized dimensions |
| Faster queries | Less redundancy |
| More storage | Less storage |
| Simple | Complex |

## Transactions & Concurrency Control

A **Transaction** is a sequence of one or more SQL operations that are executed as one logical unit of work.
* Either everything succeeds or everything fails.

### Transaction Lifecycle
```
BEGIN  -->  SQL Statements  -->  ...  -->  COMMIT
```
or
```
BEGIN  -->  SQL Statements  -->  ...  -->  ROLLBACK
```

* **BEGIN Transaction:** Starts a transaction (`BEGIN;` or `START TRANSACTION;`).
* **COMMIT:** Makes all changes permanent (`COMMIT;`).
* **ROLLBACK:** Cancels everything since transaction started (`ROLLBACK;`).
* **SAVEPOINT:** Rollback to a specific point rather than everything.
  ```sql
  SAVEPOINT save_point_name;
  ROLLBACK TO save_point_name;
  ```
* **Auto Commit:** Many databases default to Auto Commit. To control transactions, disable auto-commit or explicitly start a transaction (behavior depends on the DBMS and client).

### Transaction States
1. **Active:** Transaction currently executing.
2. **Partially Committed:** All SQL statements executed; waiting to make changes permanent.
3. **Committed:** Transaction successful; changes saved permanently.
4. **Failed:** Transaction failed due to error.
5. **Aborted:** Rollback completed; database restored.
6. **Terminated:** Transaction finished; resources released.

### What Happens if Database Crashes?
Database checks transaction status. Committed? Keep changes. Not committed? Rollback. This is possible because of recovery mechanisms (such as transaction logs).

### Concurrency Control
**Concurrency Control** is the mechanism used by a DBMS to ensure that multiple concurrent transactions execute correctly without violating data consistency.
* **Transaction Schedule:** The order in which operations from multiple transactions execute.
* **Types of Schedules:**
  * **Serial:** One after another. Safe, simple, slow.
  * **Concurrent:** Transactions overlap. Fast, needs concurrency control.
* **Serializability:** A concurrent schedule is **Serializable** if its result is the same as some serial execution of those transactions.
* **Why Serializability?** Because serial execution is always correct. Concurrency Control tries to achieve serial-like correctness without sacrificing performance.

## Deadlock

A **Deadlock** occurs when two or more transactions are waiting indefinitely for each other to release resources (transactions wait for each other forever).

### Coffman Conditions
A deadlock can occur **only if all four of these conditions hold simultaneously**:
1. **Mutual Exclusion:** A resource can be used by only one transaction at a time. Without Mutual Exclusion, deadlocks cannot occur.
2. **Hold and Wait:** A transaction already holds one resource while waiting for another.
3. **No Pre-emption:** Resources cannot be forcibly taken away. Only the transaction holding the lock can release it.
4. **Circular Wait:** Transaction A waits for B, B waits for C, and C waits for A (a cycle).

### Wait-For Graph (WFG)
* Represents waiting relationships between transactions.
* `Nodes = Transactions`, `Edges = Waiting`.
* Graph contains cycle = Deadlock exists.
* DBMS periodically checks Wait-For Graph. If cycle found = Deadlock detected.

### Deadlock Recovery
Most common approach: Choose one transaction as **Victim**, rollback victim, release locks, and allow other transactions to continue.
* **Choosing Victim:** DBMS tries to minimize cost. Factors include:
  * Amount of work already done
  * Number of rows modified
  * Number of locks held
  * Estimated rollback cost
  * Transaction priority

### Deadlock Prevention
Instead of detecting, prevent deadlock by breaking one Coffman Condition.
* **Resource Ordering:** Always acquire resources in the same order (`A => B`, but not in reverse order; circular wait can never occur).
* **Lock Timeout:** If a transaction waits too long, the database automatically aborts it.

### Deadlock Avoidance
Different from prevention. Uses additional information to decide whether granting a lock is safe.
* Classic algorithm: **Banker's Algorithm**.

### Deadlock vs Starvation
* **Deadlock:** Transactions wait forever because they wait for each other.
* **Starvation:** Transaction never gets resource because others always get priority.

## Partitioning, Replication & Sharding

### Partitioning
**Partitioning** is the process of dividing a large table or index into smaller, independent pieces called **partitions**, while allowing applications to query the table as if it were a single table.
* **Benefits:** Faster queries (when only a few partitions are needed), easier maintenance, faster backups/restores (at partition level), easier archival, faster bulk deletes, better scalability.
* **Partition Pruning:** Without Partitioning -> Search All Partitions; With Partition Pruning -> Search Only Relevant Partitions.

#### Types of Partitioning
* **Range Partitioning:** Most common. Rows assigned based on a range.
* **List Partitioning:** Rows assigned based on specific values (e.g., `PARTITION BY LIST(department)`: HR, Sales, etc.).
* **Hash Partitioning:** Uses Hash Function. Good for evenly distributing data, poor for range queries.
* **Composite Partitioning:** Uses multiple strategies (e.g., first range, then hash).
* **Horizontal vs Vertical Partitioning:**
  * Horizontal Partitioning: Row splitting.
  * Vertical Partitioning: Column splitting.
* **Local Index vs Global Index:**
  * Local Index: Each partition has its own index.
  * Global Index: Single index covers all partitions.

### Replication
**Replication** is the process of maintaining multiple copies of the same database on different servers.
* **Goals:** High Availability, Fault Tolerance, Load Balancing, Disaster Recovery, Faster Reads, Geographic Distribution.

### Sharding
**Sharding** is the process of splitting a database horizontally across multiple independent database servers called **shards**.
* If Replication solved the problem of high availability and read scalability, then **Sharding solves the problem of unlimited database growth**.
* Each shard stores **only a portion of the data**.
* *Example:* If `users` table contains 10 Million users:
  * Shard 1: 1 to 3 Million Users
  * Shard 2: 4 to 6 Million Users
  * Shard 3: 7 to 10 Million Users
* **Scaling:**
  * Vertical Scaling: Adding more resources to a single server.
  * Horizontal Scaling: Adding more servers to store more data. Sharding enables horizontal scaling.
* **Shard Key:** The attribute used to determine which shard stores a particular row.
* **Types of Sharding:** Range Sharding, Hash Sharding, Directory Sharding, Geo Sharding.

### Partitioning vs Sharding
* **Partitioning:** Splits data inside **one** database.
* **Sharding:** Splits data across **multiple** database servers.

### Database Recovery
**Recovery** is the process of restoring a database to a correct and consistent state after a failure.

## Triggers, Stored Procedures, Functions & Cursors

### Triggers
A **Trigger** is a stored database object that automatically executes in response to a specified database event (insert, update, delete). We can create a trigger or let the database do it automatically.

* **Types of Triggers:** `INSERT` Trigger, `UPDATE` Trigger, `DELETE` Trigger.
* **Timing of Trigger:**
  * `BEFORE`: Runs before the SQL statement is applied.
  * `AFTER`: Runs after the SQL statement has successfully completed.
  * `INSTEAD OF`: Mainly used on Views; executes custom logic instead of the original statement.
* **Execution Level:**
  * **Row-Level Trigger:** Runs once for every affected row.
  * **Statement-Level Trigger:** Runs once per SQL statement, regardless of how many rows are affected.
* **Recursive Triggers:** Suppose Trigger updates the same table. That update fires the trigger again, leading to a possible infinite loop.
* **Trigger Order:** Multiple triggers can exist for the same event. Some DBMSs allow controlling execution order; others have predefined behavior.

#### Trigger Code Snippets

**General Syntax:**
```sql
CREATE TRIGGER trigger_name
[BEFORE | AFTER] [INSERT | UPDATE | DELETE]
ON table_name
FOR EACH ROW
BEGIN
    -- Your executable trigger code goes here
END;
```

**Example Trigger Structure:**
```sql
CREATE TRIGGER trigger_name
AFTER INSERT
ON employees
FOR EACH ROW
BEGIN
    -- Trigger Logic
END;
```

**Practical Example (Logging User Signups):**
```sql
CREATE TRIGGER log_user_signup
AFTER INSERT ON users
FOR EACH ROW
BEGIN
    INSERT INTO audit_log (user_id, action, action_time)
    VALUES (NEW.id, 'SIGNUP', CURRENT_TIMESTAMP);
END;
```

### Cursors
A **Cursor** is a database object that allows a program or stored procedure to retrieve and process query results **one row at a time**.

* **Result Set:** A cursor operates on a Result Set (e.g., `SELECT name, salary FROM employees;` -> `(Alice, Bob, Charlie)`). The cursor moves through these rows using a pointer.
* **Cursor Life Cycle (4 Steps):**
  1. **Declare:** Tell database which query the cursor will execute.
  2. **Open:** Execute the query; database creates the result set.
  3. **Fetch:** Retrieve one row, then another, so on.
  4. **Close:** Release memory and resources.

#### Types of Cursors
* **Forward Only:** Can move only forward.
* **Scrollable:** Can move forward and backward.
* **Read Only:** Can only read data; cannot update rows.
* **Updateable:** Allows reading and modifying current row.
* **Implicit Cursor:** Created automatically by DB for internal operations.
* **Explicit Cursor:** Created manually by user/programmer.

## NoSQL & Database Models

### SQL vs NoSQL
* **SQL:** Fixed Schema | Vertical Scaling (One Big Server)
* **NoSQL:** Flexible Schema | Horizontal Scaling (Designed to scale across Server1, Server2, Server3, etc.)

### Types of NoSQL Databases
1. **Key-Value**
2. **Document**
3. **Column Family**
4. **Graph**

### ACID vs BASE

| ACID | BASE |
| --- | --- |
| Strong consistency | Basically Available |
| Immediate consistency | Soft State |
| Strict transactions | Eventually Consistent (in many systems) |

### ACID Properties
* **Atomicity:** All operations in a transaction succeed, or all are rolled back.
* **Consistency:** Data remains in a valid state adhering to constraints before and after transactions.
* **Isolation:** Concurrent transactions execute without interfering with each other.
* **Durability:** Once committed, changes survive system failures.
